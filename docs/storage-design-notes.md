# Storage lifetime e backup completo

La persistenza mobile usa un singolo database SQLite locale tramite Expo SQLite. Le sessioni restano righe compatte e indicizzate; gli aggregati lifetime e il reward ledger vengono aggiornati nella stessa transazione con WAL e `synchronous=FULL`. Il ledger separa premio sessione, missioni giornaliere e achievement, usa identificativi deterministici con `INSERT OR IGNORE` e viene ricostruito una sola volta per le installazioni precedenti. Le colonne `time_confidence` e `reward_policy` distinguono rispettivamente orari esatti/ricostruiti/approssimati e la politica economica legacy da quella nuova `completed-only`. La baseline `rewardedBrushingSeconds` conserva le monete maturate prima della migrazione, mentre i nuovi tentativi incompleti non producono XP o monete. Il ledger acquisti conserva `itemId`, prezzo pagato e data; la normalizzazione di un inventario legacy viene riscritta subito, quindi il saldo non dipende più dai prezzi correnti del catalogo. Le cadute BLE alimentano una coda bounded di fallback correlati per dispositivo e contatore atteso. Il record GATT autorevole sostituisce il fallback con una compensazione contabile che preserva sessioni intervenienti e non duplica reward. La timeline dell’interfaccia legge soltanto le ultime 120 righe, mentre il backup esporta tutte le righe e il ledger senza un limite applicativo.

Il ripristino crea prima uno snapshot del database corrente e registra due livelli di journal persistente: uno per il rollback SQLite e uno per il commit coordinato di profilo, personalizzazioni, preferenze e premi. Un token scritto atomicamente nel database decide al bootstrap se completare il nuovo stato o ripristinare quello precedente. Prima del restore, un archivio completo viene rigiocato in ordine deterministico con `getEachAsync`: conteggi, durata, XP, collezionabili, reward base e achievement indipendenti dal calendario devono coincidere con le sessioni senza caricare l’intero archivio in memoria. I bonus locali vengono verificati contro gli aggregati esportati. Questa separazione evita falsi rifiuti quando il nuovo dispositivo usa un fuso orario diverso. Una barriera applicativa accoda le sessioni BLE/manuali che arrivano durante il restore, così vengono salvate subito dopo senza essere sovrascritte. Se la copia, la validazione o il processo vengono interrotti, lo stato coerente viene recuperato al prossimo avvio. Un backup nato da un vecchio codice v2 conserva gli aggregati lifetime originali e viene marcato `historyComplete=false`: i progressi non vengono azzerati, mentre l’app dichiara onestamente quante righe storiche erano contenute nel vecchio formato.

Fonti ufficiali consultate:

- Expo SQLite SDK 54: https://docs.expo.dev/versions/v54.0.0/sdk/sqlite/ — `openDatabaseAsync`, WAL, query parametrizzate e transazioni esclusive.
- Expo FileSystem SDK 54: https://docs.expo.dev/versions/v54.0.0/sdk/filesystem/ — `FileHandle`, lettura bounded dell’header e file temporanei in cache.
- Expo Sharing SDK 54: https://docs.expo.dev/versions/v54.0.0/sdk/sharing/ — condivisione di file locali su iOS/Android.
- Expo DocumentPicker SDK 54: https://docs.expo.dev/versions/v54.0.0/sdk/document-picker/ — selezione con `copyToCacheDirectory: true` per lettura immediata.

Il backup completo è un file versionato `.brushlings` condivisibile. L’header SQLite viene validato con una lettura bounded di 100 byte prima dell’apertura. Una allowlist su `sqlite_schema` accetta soltanto le tabelle e gli indici del formato; trigger, view e oggetti sconosciuti vengono rifiutati prima della copia nel database principale. Durante l’esportazione, la copia in cache sostituisce gli ID sessione device legacy e le chiavi cursore con alias deterministici derivati da SHA-256; una guardia finale rifiuta eventuali MAC o UUID rimasti negli ID. Reward ledger e progressione vengono rigiocati sulla copia e il manifest usa gli aggregati risultanti, così un cambio di fuso non crea una contraddizione interna. Il database locale resta invariato. Date, durate e dati di progressione rimangono nel file perché necessari al restore completo. Il formato precedente a codice resta importabile per retrocompatibilità; i backup nuovi non sono troncati a 120 sessioni.
